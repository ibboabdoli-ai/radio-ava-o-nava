# Radio Ava o Nava platform and isolated staging

This branch integrates the local candidate with PR #27 without changing the live radio player, production database or Clubhouse account. The PR #27 landing page remains at `v2/request-song.html`; it links to the authenticated Persian user/admin interface at `v2/radio-club.html`. The tracked `v2/request-config.json` remains disabled for the live site. An isolated, generated copy of the UI and API is deployed on the staging Worker; see [STAGING_DEPLOYMENT_REPORT.md](../STAGING_DEPLOYMENT_REPORT.md).

## Database and API

The verified staging D1 received `schema.sql`, `attendance.sql`, `migrations/0002_radio_platform.sql`, `migrations/0003_auth_recovery.sql`, and `migrations/0004_auth_atomic_recovery.sql` in that order. Do not rerun `0002` on this database: it rebuilds `song_requests`. It preserves legacy requests but does not import old `listener_scores`, because those observations do not prove attendance. `0003` adds one-time recovery codes; `0004` makes password changes, code consumption and session revocation atomic through a D1 trigger.

`worker.js` delegates to `platform-worker.js`. `GET /health` only reports process/config status. All other routes require `RADIO_FEATURES_ENABLED=true`. Registration additionally requires `REGISTRATION_ENABLED=true`. The isolated staging Worker serves both frontend and API at one `workers.dev` HTTPS origin; live browser login and cookie behavior were verified. `AUTH_RATE_SECRET` is a random Worker secret. No credentials or API keys belong in site files.

Public routes: `GET /api/catalog?q=`, `/api/queue`, `/api/leaderboard`; `POST /api/auth/register`, `/api/auth/login`, `/api/auth/logout`, `/api/auth/recover`. Authenticated listener routes: `GET/PATCH /api/me`; `POST /api/me/password`, `/api/me/recovery-code`; `GET/DELETE /api/me/clubhouse-identity`; `GET /api/me/transactions`, `/api/me/attendance`, `/api/me/requests`; `POST /api/requests` with `catalogSongId` and a UUID `Idempotency-Key`; `PATCH /api/me/requests/:id` to cancel. Admin session routes: `POST /api/admin/catalog`, `PATCH /api/admin/catalog/:id`, `GET/PATCH /api/admin/requests`, `GET /api/admin/users`, `PUT /api/admin/users/:id/clubhouse-identity`, `POST /api/admin/users/:id/adjust-points`, `GET /api/admin/leaderboard`, `POST /api/admin/maintenance`.

New passwords use Node's built-in `scrypt` with unique 256-bit random salts and OWASP-listed parameters `N=8192, r=8, p=10`; the stored hash is scheme-tagged. A successful login upgrades an old 100,000-round PBKDF2 hash and revokes older sessions. Both staging QA accounts are now on scrypt. Recovery uses one random 256-bit code, shown once, stored only as a SHA-256 hash and consumed atomically with the password update. Password changes revoke all sessions and recovery codes in the same D1 statement. A user without a saved recovery code needs manual identity verification; no email identity has been established. Cookies are `HttpOnly`, `Secure`, `SameSite=Lax`, scoped to `/api`; only token hashes are stored. Mutations require an exact `Origin`; CORS allows only that origin. A configured `ALLOWED_ORIGIN` and random `AUTH_RATE_SECRET` are required. Authentication attempts are limited by hashed IP and username. Public queue omits requester names; leaderboard requires explicit opt-in. Admin actions are recorded in `admin_events`. Retention maintenance removes expired sessions, observations older than 90 days, closed attendance sessions older than 365 days, and old rate-limit entries; schedule this after privacy review. The legacy `listener_scores` table remains for a separate reviewed retention decision and is never used for new points. Errors are logged without request bodies or tokens.

No public admin creation endpoint exists. After registering a designated staging administrator, promote only that account through reviewed, access-controlled D1 SQL, for example `UPDATE users SET role='admin' WHERE username='staging_admin';`. Verify the exact target user and database before execution. Admin identity mapping requires recorded consent; use a stable Clubhouse numeric/user ID, never a display name.

## Points and music rules

The only attendance input is `POST /api/internal/attendance`, protected by `ATTENDANCE_OBSERVER_ENABLED=true` and a separate `OBSERVER_TOKEN`. It accepts a stable Clubhouse ID, room ID, state (`seen`/`left`) and unique UUID observation ID; the Worker sets receipt time. The endpoint is **disabled by default**. There is no verified live Clubhouse presence observer. Bot messages, inferred `user.joined` events and old PR #27 observations cannot earn points. First observation earns zero. Consecutive `seen` observations in one room at most 75 seconds apart accrue observed time. A `left`, room change or longer gap ends a session without crediting the unobserved interval. Complete accumulated minutes credit once through a D1 trigger and unique ledger entries.

An admin must manually verify the music source, playability and usage rights before adding a catalog item. The current code accepts only `https://audius.co` links; a link alone is **not** proof of rights or playability. A request starts pending at no cost. Approval atomically checks the current point ledger, inserts one spend and moves the request to approved. Rejection or cancellation of an approved request refunds once. Legacy PR #27 requests have no user account or point cost; admins can still approve/reject them without inventing a charge. Marking a song played does not start playback. The queue is moderated and may be reprioritized. The radio stream and player are untouched.

## Verification

From repository root: `node --test backend/tests/*.test.mjs` and `node --test v2/tests/*.test.mjs`. From `backend`: `npm run check` and `npm test`. Local backend tests use `node:sqlite` in memory and mock HTTP requests. The staging report records actual remote D1, Worker, HTTPS API and browser checks. Live Clubhouse compatibility, real attendance, music rights and mobile playback remain unverified.

Before production: perform an independent authentication and abuse-resistance review, establish recovery support for users who lose their one-time code, provide a privacy notice and retention schedule, and confirm rights for each real catalog entry. Keep registration closed until that review passes. Do not enable observer input until a lawful, independent, reliable source of room presence is demonstrated. A separate test Clubhouse account and explicit approval are required before any live Clubhouse experiment. No production merge, deployment, or real message is authorized by this staging work.
