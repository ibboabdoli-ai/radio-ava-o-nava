# Radio Ava o Nava platform candidate (local branch only)

This branch extends PR #27 without changing the live radio player, production database, Clubhouse account or deployed Worker. `v2/radio-club.html` is the Persian user/admin interface. `v2/request-song.html` points to it. `v2/request-config.json` has an empty `apiBase`, so the page remains disabled until a reviewed staging API is configured.

## Database and API

Apply `schema.sql`, then `attendance.sql`, then `migrations/0002_radio_platform.sql` to a **new staging D1 database**. Back up a populated PR #27 database before migration: `0002` rebuilds `song_requests`. It preserves legacy requests but does not import old `listener_scores`, because those observations do not prove attendance. The migration is one-time, not repeatable. Check schema and data before applying it anywhere beyond disposable staging.

`worker.js` delegates to `platform-worker.js`. `GET /health` only reports process/config status. All other routes require `RADIO_FEATURES_ENABLED=true`. Registration additionally requires `REGISTRATION_ENABLED=true`. Set `ALLOWED_ORIGIN` to the exact website origin. Use a same-site HTTPS API subdomain for browser cookies. Never set `apiBase` to a `workers.dev` origin without verifying cookie behavior. `AUTH_RATE_SECRET` must be a random secret. No credentials or API keys belong in site files.

Public routes: `GET /api/catalog?q=`, `/api/queue`, `/api/leaderboard`. Cookie-based listener routes: `POST /api/auth/register`, `/api/auth/login`, `/api/auth/logout`; `GET/PATCH /api/me`; `GET/DELETE /api/me/clubhouse-identity` to inspect or revoke the mapping; `GET /api/me/transactions`, `/api/me/attendance`, `/api/me/requests`; `POST /api/requests` with `catalogSongId` and a UUID `Idempotency-Key`; `PATCH /api/me/requests/:id` to cancel. Admin session routes: `POST /api/admin/catalog`, `PATCH /api/admin/catalog/:id`, `GET/PATCH /api/admin/requests`, `GET /api/admin/users`, `PUT /api/admin/users/:id/clubhouse-identity`, `POST /api/admin/users/:id/adjust-points`, `GET /api/admin/leaderboard`, `POST /api/admin/maintenance`.

Passwords use PBKDF2 SHA-256 with unique salts; only session token hashes are stored. Cookies are `HttpOnly`, `Secure`, `SameSite=Lax`. Cross-origin mutations require an exact `Origin`; response CORS allows only that origin. A configured `ALLOWED_ORIGIN` and random `AUTH_RATE_SECRET` are required when features are enabled. Registration/login have an IP-hash attempt limit. Public queue omits requester names; leaderboard requires explicit opt-in. Admin actions are recorded in `admin_events`. Retention maintenance removes expired sessions, observations older than 90 days, closed attendance sessions older than 365 days, and old IP hash limits; schedule this after privacy review. The legacy `listener_scores` table remains for a separate reviewed retention decision and is never used for new points. Errors are logged without request bodies or tokens.

No public admin creation endpoint exists. After registering a designated staging administrator, promote only that account through reviewed, access-controlled D1 SQL, for example `UPDATE users SET role='admin' WHERE username='staging_admin';`. Verify the exact target user and database before execution. Admin identity mapping requires recorded consent; use a stable Clubhouse numeric/user ID, never a display name.

## Points and music rules

The only attendance input is `POST /api/internal/attendance`, protected by `ATTENDANCE_OBSERVER_ENABLED=true` and a separate `OBSERVER_TOKEN`. It accepts a stable Clubhouse ID, room ID, state (`seen`/`left`) and unique UUID observation ID; the Worker sets receipt time. The endpoint is **disabled by default**. There is no verified live Clubhouse presence observer. Bot messages, inferred `user.joined` events and old PR #27 observations cannot earn points. First observation earns zero. Consecutive `seen` observations in one room at most 75 seconds apart accrue observed time. A `left`, room change or longer gap ends a session without crediting the unobserved interval. Complete accumulated minutes credit once through a D1 trigger and unique ledger entries.

An admin must manually verify the music source, playability and usage rights before adding a catalog item. The current code accepts only `https://audius.co` links; a link alone is **not** proof of rights or playability. A request starts pending at no cost. Approval atomically checks the current point ledger, inserts one spend and moves the request to approved. Rejection or cancellation of an approved request refunds once. Legacy PR #27 requests have no user account or point cost; admins can still approve/reject them without inventing a charge. Marking a song played does not start playback. The queue is moderated and may be reprioritized. The radio stream and player are untouched.

## Offline checks

From repository root: `node --test backend/tests/*.test.mjs` and `node --test v2/tests/smoke.test.mjs`. From `backend`: `npm run check` and `npm test`. The backend tests use Node 22 `node:sqlite` in memory and mock HTTP requests; no account, Clubhouse network, Cloudflare deployment or paid service is used. The SQL trigger and Worker logic are exercised locally, but D1 production behavior, live Clubhouse compatibility, browser cookie configuration, music rights and mobile playback still require separate review and validation.

Before any staging deployment: run D1 migration against a fresh staging database, verify same-site cookies and CORS, provide a privacy notice and retention schedule, confirm rights for each catalog entry, and conduct a security review. Do not enable observer input until a lawful, independent, reliable source of room presence is demonstrated. A separate test Clubhouse account and explicit approval are required before any live Clubhouse experiment. No production merge, deployment, or real message is authorized by this candidate.
